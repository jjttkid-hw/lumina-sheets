# Lumina 性能基准

2026-09-21 已完成当前 0.29.0 制品的 Chrome/Firefox/WebKit 两档实存数据测量、编辑和范围公式核验，原始样本、环境、制品哈希及边界见 [三引擎报告](acceptance/browser-performance-2026-09-21/README.md)。这是新的实际测量，不沿用下文 v0.3/v0.5 历史数字；没有设置商业性能预算或宣称全平台通过。

性能页相关指标必须以当前浏览器、数据规模和操作脚本的实测结果为准。项目没有把第三方产品宣传数字当作本地保证；基准结果会同时记录逻辑行列数、实际填充单元格数、可见绘制量、公式目标数、编辑延迟和可观察内存数据。

性能基准模块位于 `src/lib/performance/harness.ts`，不依赖 React 或 DOM。它可以在 Vitest/Node 运行，也可以从浏览器诊断面板调用：

- `createBenchmarkWorkbook` 创建百万行、XFD 列上限的稀疏工作簿。逻辑尺寸不会分配对应数量的行对象。
- `benchmarkViewport` 重复执行行列可视区计算和合并区间查询，输出样本耗时分布及 p50/p95/p99。
- `benchmarkCalculations` 调用与计算 Worker 相同的安全公式引擎。
- `benchmarkEditLatency` 测量编辑一个值并读取依赖公式的耗时。
- `benchmarkPatches` 测量持久化日志的补丁回放吞吐，不能用该值替代编辑热路径延迟。
- `RenderMetricsCollector` 接收 Canvas 的 `onRenderMetrics` 回调，记录绘制耗时、绘制单元格数和 DOM 节点数。
- `sampleMemory` 在支持的 Chromium 环境读取 `performance.memory`，在 Node 环境读取 `process.memoryUsage()`。
- `runPerformanceBenchmark` 汇总上述结果，并按调用方提供的预算生成 PASS/FAIL。没有设置预算时只报告 MEASURED；通过自定义预算不代表商业认证。

示例：

```ts
import {
  createBenchmarkWorkbook,
  runPerformanceBenchmark,
  formatBenchmarkReport,
} from './src/lib/performance/harness';

const report = runPerformanceBenchmark({
  workbook: createBenchmarkWorkbook({
    rows: 1_000_000,
    cols: 16_384,
    populatedRows: 10_000,
    populatedCols: 8,
    formulas: true,
  }),
  viewport: { iterations: 120, warmupIterations: 8 },
  calculation: { targetCount: 10_000 },
  edit: { iterations: 100 },
  patches: { patchCount: 100 },
  budget: { viewportP95Ms: 16, calculationMs: 250 },
});
console.log(formatBenchmarkReport(report));
```

Canvas 组件会把实际绘制数据写入 `canvas.dataset.renderMs`、`canvas.dataset.paintedCells` 和 `canvas.dataset.renderCount`，并通过 `onRenderMetrics` 交给 `RenderMetricsCollector`。因此“单元格数量”应区分逻辑工作表规模和当前视区绘制量。

## 解释结果

- `viewport p95` 接近或低于 16ms，表示在 60Hz 帧预算内完成几何计算；完整 Canvas 绘制还应使用组件回调测量。
- `edit-latency p95` 表示当前主线程编辑与公式读取的本地延迟。Worker 计算需要单独记录消息往返时间。
- `averagePaintedCells` 应接近视区行数乘以视区列数，而不应接近工作表逻辑大小。
- 内存字段可能为空：标准浏览器通常不暴露精确堆内存。缺少该字段不能推断没有内存增长。

基准结果只描述运行基准的机器和浏览器，不代表云端并发、多人协作、网络吞吐、Excel 全兼容或商业 SLA。后续发布应把浏览器版本、设备、逻辑数据规模和基准脚本一起归档。

## 浏览器性能面板

`PerformanceLab` 使用产品实际 `Spreadsheet` 组件，可切换 100,000 与 1,000,000 个真实存储单元格。两档都设置 1,000,000 逻辑行和 256 逻辑列：前者填充 10,000 行 × 10 列，后者填充 100,000 行 × 10 列，其余行保持空白。每行包含一个真实公式。

数据在专用 Worker 生成，每批 5,000 个单元格传入主线程。`dataReadyMs` 计时到全部数据进入主线程并准备完成，`firstDrawMs` 计时到该工作表的第一次 Canvas 绘制完成；两者均从点击“加载数据”开始。后台公式测量使用 Worker 驻留数据，分别报告计算耗时和消息往返耗时；单次运行不提供伪造的 P95。界面支持跳转至百万行、40 次跨视区采样、真实单元格编辑和导出 JSON 报告。

Canvas P95 来自实际绘制回调；它不是整个浏览器帧时长，也不会换算为 FPS。编辑指标从提交值到包含该修改的同一工作表版本完成 Canvas 绘制计时，仅采集修改坐标处于当前可视区的样本。同一次绘制前合并的多次提交只保留最后一次，因此它不是逐按键输入延迟或浏览器合成帧提交延迟。内存计数器仅在浏览器公开时显示，通常不包含 Worker 堆，因此报告保留这一限制。

## 采样口径与限制

- 通过 Canvas 元素及 `renderCount` 去重回调；每次真实绘制最多收集一次。同一视区发生两次真实重绘时，两次均计入，不能将该数量称为屏幕刷新帧数。
- “跨视区采样”依次访问 24 个已填充区位置和 16 个全表位置，后者包括空白行及百万行边界。汇总包含重置以来保留的实际绘制（最多最近 10,000 条），包括切换位置时的中间绘制，因此不是一百万行密集填充数据的绘制基准。
- 每个目标位置必须进入可视区并完成 Canvas 绘制后才推进，最后一个目标实际绘制后才显示完成；超时标记为未完成。页面切入后台会主动中止运行，避免后台 `requestAnimationFrame` 暂停造成虚假的完成结论。
- 首次 Canvas 绘制和编辑计时截止于绘制命令完成，不包含浏览器合成器呈现到屏幕的时间。
- 后台公式测量是单次运行且只返回首尾校验值、数量和计时。计算内部耗时与完整消息往返耗时分别展示，不从单次结果推导 P95。
- 10 万单元格档的默认公式校验值为 J1 = 5、J10000 = 50,000；100 万单元格档为 J1 = 5、J100000 = 500,000。这些是确定性校验值，不是浏览器性能测量结果。

## v0.5 范围依赖更新基准

性能页的“范围公式更新基准”在专用 Worker 中比较同一安全公式引擎的增量失效与清空缓存后的全量重算。默认使用 10,000 个公式、30 次修改；结果包含每次样本和索引计数，可用“导出范围报告”归档。它不包含 Canvas、网络、Worker 消息往返，也不是 SpreadJS 或其他第三方产品的对照测试。

2026-09-18，生产预览构建在 Chromium 153、15 个逻辑处理器上完成两种布局。独立范围将每个公式绑定到 4 个独立输入；重叠范围让全部公式绑定同一段输入，因此用于展示索引在密集重叠下的实际边界。

| 指标                            | 10,000 个独立范围 | 10,000 个重叠范围 |
| ------------------------------- | ----------------: | ----------------: |
| 公式 / 实际存储单元格           |   10,000 / 50,000 |   10,000 / 10,004 |
| 依赖失效 P95                    |           0.20 ms |          12.60 ms |
| 增量读取 P95                    |           6.40 ms |          31.60 ms |
| 全量重算 P95                    |          74.10 ms |          26.80 ms |
| 平均实际重算                    |                 1 |            10,000 |
| 平均范围候选检查 / 索引节点访问 |       13.0 / 26.7 |   10,000 / 20,000 |

原始数据：[独立范围](artifacts/ranges-v05-disjoint.json)、[重叠范围](artifacts/ranges-v05-overlapping.json)。独立布局的增量路径保留 9,999 个缓存；重叠布局需要清除全部结果，增量路径因此可能比同一引擎的全量重算更慢。这是用于验证选择性失效和最坏重叠边界的可重复样本，不是跨设备 SLA 或商业认证。


## 采样容量与预算有效性

绘制与可见编辑的收集器各自默认保留最近 10,000 条有效样本，以环形缓冲覆盖较早样本，插入成本不随已观测数量增加。报告的 frames 是保留数，observedFrames 是重置以来有效总数，droppedFrames 是因容量移除的数量，sampleLimit 是配置上限；所有均值与分位数仅基于保留样本。导出原始 samples 按时间顺序排列，返回副本防止外部修改污染统计。无效耗时、格数、节点数或时间戳不计为有效观测。清空样本同时重置这些计数。

本地基准的 viewportP95Ms/calculationMs/patchP95Ms 必须是有限非负数，未知预算键、NaN、Infinity、负值及非法容器在执行测量前拒绝；未配置仍只报告 MEASURED。此修复不能追溯验证旧报告，不代表已完成当前浏览器验收。环形缓冲控制的是采样内存与统计上限，不证明表格主流程性能。


清空测量时会同时清除待计算请求、结果、绘制/编辑样本和跨视区完成状态，旧请求的成功或错误不再回填。数据准备/首次绘制属于已加载数据的生命周期信息，清空样本不重新加载数据也不清除这些信息；底层正在执行的同步 Worker 计算可能继续，清空只是失效该次测量。新计算开始时隐藏上一次结果，计算错误按请求 ID 匹配；通信失败关闭线程并要求重新加载数据，避免主线程编辑与 Worker 驻留数据分离后仍输出计时。重新加载后不接收旧线程的任何消息。界面状态测试不能证明浏览器实际线程性能或响应时间。


## 报告来源

性能实验室导出的 JSON 含 schema:1 与 build 字段。构建工具嵌入产品版本、production/development 模式、源码摘要 sourceSha256、文件数及来源时间/来源类型；未运行该工具时 build 为 null，不猜测当前版本。摘要涵盖 src/public/examples/scripts、package 与锁文件、入口 HTML、Vite 和 TypeScript 构建配置，文件列表按相对路径排序，不含开发机绝对路径或文件时间戳。证据文档变动不改变源码摘要，实际运行输入变化会改变；开发服务器只在启动时计算，HMR 后可能过时，不能用开发模式报告作为正式候选验证。

源码摘要不涵盖安装依赖实际字节、构建工具运行环境或最终产物，不能替代 siteSha256 和 SDK tgz 摘要。正式验收仍必须使用发布门禁记录的同一站点/安装包，另保存浏览器版本、操作及原始报告；build 元数据只用于追溯和发现明显版本混用，不自动授予性能通过状态。


范围公式面板遵循同样的构建追溯约定：导出含 schema/build，并保留原有 version:'0.5' 作为历史基准格式标识，不代表当前产品版本。完成提示、公式数量及迭代说明取自实际 report，界面不再显示误导性的产品 v0.5。线程构造/发送失败会结束忙碌状态并提示重试；取消、崩溃和卸载均清除线程所有权，迟到进度/结果不得提交。修改公式分布会清除旧结果和完成提示，必须重新测量。这些保护不改变范围基准的测量顺序与比较口径。
